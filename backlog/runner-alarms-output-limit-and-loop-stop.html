Runner alarms: what the Mendel logs say

Scouting page for backlog/runner-alarms-output-limit-and-loop-stop.md. Built 2026-09-04 from 65 session logs (41 on this box in ../mendel-benchmark/benchmark/runs/, 24 on the Mac under ~/.local/share/choose-a-local-llm/evidence/; 6 Mac files are byte-for-byte or UUID copies of files on this box and are counted once). The Mac directory ~/code/mendel-benchmark/scratchpad/benchmark/runs/ is an identical copy of evidence/mendel-issue-13-run7/ and adds nothing.

Short answer. Over 5751 assistant calls, a 20-minute cap cuts 10 (0.17%): six repetition loops that ran to maxTokens, two aborted requests, the 70-minute discarded tool call from research run 2, and one healthy 21-minute call on a replay arm running at 1.8 tokens/s. The longest healthy call in a scored run is under 8 minutes; the longest healthy cloud call is under 6. N = 20 holds; N = 25 is the choice if that replay arm must survive. The output-limit counter catches a different failure: a small local model that thinks for 9 to 11 minutes, hits its 16k output budget with no tool call, and does it again on the next turn. Piece 3 as written ("on tool calls") never fires in these logs: only 4 length stops carry a tool call and none are consecutive. Counting every length stop, 8 sessions have two in a row, but two of them are complete, scored runs where a context overflow, not the output budget, produced the pair. Counting only stops at the real output budget, 3 sessions have the pair and all 3 are failed runs. Details below.

How each column is computed

  • Formats. Three log shapes exist. pi session (*-session.jsonl, first record type: session): one record per message. pi events (*-events.jsonl, written by run-pi-rpc.mjs): the RPC event stream, used only for the one run that has no session file (run2-replay-embedded-repeat) and for loop verdicts. claude-code (haiku/opus/sonnet-*.jsonl): the Claude Code transcript, one record per streamed content block.
  • turns. One assistant message = one API call. pi: records with message.role == assistant, the same rule as count-tool-calls.mjs (commit fe6da234). claude-code: distinct message.id among type: assistant records. gemma-4-26b-a4b stops at line 236, as runs/SESSIONS.md requires.
  • turn duration. pi: record.timestamp (written when the message ended) minus message.timestamp (set when pi created the request). Checked against the events log of one run: message.timestamp is 4 to 8 s before message_start and the record time equals message_end to the millisecond, so the span is request-to-end and includes prompt processing and pi's automatic retries. claude-code: end timestamp of the message minus the timestamp of the record before its first block (the tool result or user message), so it also includes nothing but the API call. Aborted and error turns keep their span; they measure how long the runner or pi waited, not generation.
  • tokens. pi: usage.input + cacheRead + cacheWrite as "in", usage.output as "out". claude-code: input_tokens + cache_creation_input_tokens + cache_read_input_tokens and output_tokens. Averages are over turns.
  • peak context. Max over turns of in + out, the rule of fe6da234 (pi's usage.totalTokens). The claude-code value uses the same sum on the Anthropic usage fields, which the recompute in fe6da234 did not read.
  • tool calls, tool errors. pi: toolCall blocks in assistant messages; toolResult records with isError: true. claude-code: tool_use blocks; tool_result blocks with is_error: true.
  • nudges. pi: user messages whose text equals the runner's TOOLING_MSG or MODEL_MSG, counted from the session log. Where a -meta.json exists on the Mac its nudges arrays agree. other user msgs are any further user texts (owner help, the replay prompts). claude-code: unavailable; the SDK transcript has no nudge marker.
  • compactions. pi session: type: compaction records; pi events: compaction_start. claude-code: unavailable (no compaction record in that transcript shape).
  • output-limit hits. pi: stopReason == "length" or rawStopReason in (max_tokens, length). claude-code: stop_reason == "max_tokens". pi re-issue msgs: toolResult records whose content contains "hit the output token limit"; this is the pi message the backlog item names. Its full text: Tool call "edit" was not executed: the response hit the output token limit, so its arguments may be incomplete. Re-issue the tool call.... It appears only when the truncated message carried a tool call; a length stop inside thinking or text gets no message and the runner's model nudge or a compaction follows instead.
  • at budget. A length stop whose output is at the real output budget: 80 percent of maxTokens, the runner's own atBudget test. Every Mac -meta.json records maxTokens: 16384 for the local models, so the test is output ≥ 13,107 for them; the Fireworks DeepSeek entries stop at 384,000, so the test is output ≥ 300,000 there. A length stop below that is one of two other things: a 1-token stub from a server that refused to generate, or a context overflow where llama.cpp reports length because the window is full (output under 1,000 tokens, input near contextWindow). pi 0.84.0 and later treats a below-budget length stop as "truncated below the intended limit": it compacts and retries once, and a second one ends pi's run (pi changelog, #7540). The runner then sends a tooling nudge and pi starts again. That is why 26 length stops in the logs are followed directly by a compaction record.
  • two in a row. Pairs of consecutive turns that both hit the output limit: "any" counts every length stop, "at budget" counts only at-budget stops. Piece 3 as written counts only pairs where both carry a tool call; that count is zero everywhere, since only 4 length stops carry a tool call at all.
  • loop verdict. benchmarks/loop-check.py unchanged, window 60, threshold 0.10. It reads an events log. For runs that have one, it ran on the events log. For session-only logs, a helper wrote each assistant block (thinking, text, tool-call arguments) as one delta with a newline, in the same events shape, and loop-check ran on that. The two inputs differ for tool calls: the real event stream concatenates all tool-call arguments with no line breaks, so long runs of near-identical bash commands form one line and stay invisible; the per-block input sees them. One run (google/gemma-4-12b low guided v3) is LOOP on the per-block input ({"command": "ls -F_r"} repeated) and ok on its events log for that reason. The appendix shows both where both exist.

Four patterns sit behind the hits:

  • Cloud text loop to a 384k budget. DeepSeek on Fireworks (maxTokens 384,000) wrote the same sentence for 45 to 50 minutes, three times across two runs, plus three more calls of 190k to 320k tokens that ended in a tool call just short of the budget. No tool call was in the truncated part, so pi sent no re-issue message and the runner saw a normal model stop. Never two in a row. The loop verdict catches all three sessions; nothing else in this item does before the budget.
  • Small local model thinks to 16k and stops. google/gemma-4-12b hits 16,383 output tokens in thinking only, 9 to 11 minutes each, 4 to 6 times per run, two to four in a row. pi treats a stop at the budget as a normal stop, so the runner's model nudge follows each one. This is the "generation collapse" the scoring notes describe, and every run with this pattern was a failed run (0 commits). A 20-minute cap does not see it; a consecutive at-budget rule does, 28 to 39 minutes into the run.
  • Server-side stub stops. mlx-community/Qwen3.8-27B-4bit low (blind and guided v3) returned 1 output token with finish_reason: length 11 and 16 times: the mlx server at 88 percent of its window refused to generate. pi already handles this pair: it compacts, retries once, and ends its run on the second stub; the runner's tooling nudge restarts it, ten times, until tooling_budget_exhausted. A tooling failure, not model output. The fix is the window arithmetic in backlog/qwen38-mlx-output-budget-and-window.md, not an alarm.
  • Context overflow pairs in healthy runs. qwen3.6-35b-a3b guided and high (blind) each show a pair: a length stop with 43 or 304 output tokens at 94k of a 98k window, then a 1-token stop, then a compaction. Both runs went on to complete and score (83/100 for the guided v3 run). These pairs are pi's below-budget recovery working as designed. A rule that counts every length stop would have ended both runs about 15 minutes before they finished.

The tool-call re-issue path fired 4 times in all logs (4 sessions), never twice in a row, and every time the model recovered on the next turn. The 70-minute call from research run 2 (run2-replay-short-dry, 16,384 tokens, one toolCall block) is the only one that combined a discarded tool call with a long wall-clock, and it is a single event.

Not relevant to this item. rpiv-mono is a set of pi extensions for a human-in-the-loop workflow. Its only uses of maxTokens are (1) the pi models.json example, with maxTokens: 131072 for one cloud model, (2) the rpiv-btw side-call budget, which reserves contextWindow - maxTokens - reserve for history, the same window arithmetic our backlog item already keeps, and (3) telemetry that records turn.stop_reason = "max_tokens" as a span attribute. There is no theory of small turns, no chosen small value, and no measurement behind one. The telemetry span attribute is the one idea worth copying: it is piece 1 of this item under another name.

5. Recommendations

Piece 1: count and log. Do it first, as the item says.

Count two things separately, because they are two failures: output_limit_hits (every stopReason: length, with the block types of the truncated message) and reissue_msgs (pi's "hit the output token limit" tool result). In these logs the first is 61 events in 20 sessions and the second is 4 events in 4 sessions. Log the output-token count, the duration, and the runner's own atBudget verdict with each hit, since the 1-token server stubs, the context overflows, and the 16k thinking collapses need different fixes. One alarm line per event in the runner log. No behaviour change.

Piece 2: a per-turn wall-clock cap. N = 20 minutes.

The longest healthy call in every log is 21 m 06 s (the gemma-4-12b replay arm on the Mac, 61k context, 2,278 output tokens at 1.8 tokens/s); the longest healthy cloud call is 5 m 53 s (DeepSeek flash, 25k output tokens). p99.5 of all turns is 8 m 53 s. N = 20 min cuts 10 of 5751 calls (0.17%): six DeepSeek text loops of 31 to 50 minutes, two runner aborts of 37 and 62 minutes where no token came back, the 70-minute discarded tool call, and one healthy call: the 21-minute replay call above, on an arm that ran at 1.8 tokens/s. That arm was a research replay, not a scored configuration; the longest healthy call in a scored run is under 9 minutes. N = 25 would cut nothing healthy and still catch the 31-minute loop; it is the middle of the empty band between 21 m 06 s and 31 min. N = 15 would also cut the 18-minute 16k thinking run of prism-ml low (a length stop, so piece 3 territory), one 18-minute abort, and one 18-minute healthy replay call. N = 10 starts cutting the 10 to 11 minute gemma-4-12b thinking collapses, which is not this piece's job. Proposal: keep 20 as the item says, 170 times the median turn and above every healthy call in a scored run; move to 25 only if a replay arm that slow must survive the cap. State the end reason as turn_timeout and score the row as the item says: a stop, not a rescue.

One caveat on the measurement. Aborted turns carry the wait of the runner's stall abort and pi's retries, up to 61 minutes in the replays; the model generated nothing in them. The cap needs its own clock from message_start (or turn_start) in the RPC stream, not from the request timestamp, or it double-counts a retry. The events log has both markers already.

Piece 3: two consecutive output-limit hits. Change the condition from "on tool calls" to "at budget".

As written, the rule never fires: no log has two consecutive length stops that both carry a tool call, and the tool-call re-issue path recovered every time. The opposite rule, every length stop, fires in 8 sessions and two of them are complete, scored runs (the qwen3.6-35b-a3b context-overflow pairs above). The rule that separates the two is the runner's existing atBudget test: two consecutive length stops with output at 80 percent or more of maxTokens. That fires in 3 sessions, all gemma-4-12b, all failed runs with 0 commits, at 28, 32 and 39 minutes into runs that went on to 46, 49 and 99 minutes. It would have saved 95 machine minutes and changed no score. Below-budget pairs (the 1-token stubs, the overflows) stay with pi's own compact-and-retry and the runner's tooling budget, which already end them. End reason output_limit, with the two output-token counts in the row.

The loop verdict at run close

Run loop-check.py on the events log at run close, as the item plans, but feed it tool-call arguments one call per line. Today the events path joins all tool-call deltas into one string and the window never sees the repeated ls -d examples/... commands; the per-block input in this page saw them, and so did the earlier measure-neardup.py. That is a one-line change in read_lines: append a newline after each toolcall_end event. Verdicts here: 11 of 65 sessions LOOP on the per-block input; the three DeepSeek cloud sessions among them are the ones no other alarm in this item catches before the 384k budget, and the loop verdict is the only piece that sees a loop before it runs to the budget.
