Runner alarms: summary

The decisions, one paragraph each, with a link to the section of the full report that carries the evidence. The report is served at /history/runner-alarms-output-limit-and-loop-stop.html. It reads 65 Mendel sessions and 5,751 assistant turns from both machines.

1. Set maxTokens to 8,192 for every local model, 6,656 for Qwen3.8 on MLX

Today every pi entry says 16,384. No local model needs it. The longest healthy answer any local model produced in 2,712 turns is 4,007 tokens, one file write by gemma-4-12b. The p99 is under 1,300 tokens for every local model. Everything above that in the logs is a thinking collapse or a loop, so the budget is a waste limiter, not a quality limiter.

The rule is maxTokens = min(max(8192, pow2ceil(2 × L)), contextWindow / 4), where L is the model's longest healthy output. Twice L keeps the runner's at-budget line, 80 percent of the cap, at 1.6 times the largest real answer, so piece 3 below can never fire on legitimate work. The floor of 8,192 is twice the fleet maximum, rounded to a power of two, and it halves the cost of a collapse from 10 minutes to 5. The quarter-window term only bites Qwen3.8 MLX, whose window is 26,624.

Set pi's reserveTokens to the same value. It defaults to 16,384 and drives compaction on its own, so leaving it alone keeps 8k of window reserved for an answer that can never be that long. A dynamic cap, window minus the current prompt, solves fit but does nothing for collapse. Keep both as min(static, dynamic).

2. For a new model, a 10-minute probe sets the first value and one scored run confirms it

Three single calls, no agent loop. A prompt at 60 percent of the window checks fit and prefill speed. A request to write one complete 400-line file, thinking on, cap at 16,384, gives a lower bound for L and shows whether the model can end a file. A deliberately failing edit followed by the retry reproduces the trigger of every gemma collapse in the logs. Failure signs: length with 0 or 1 tokens, length at 16,384 on the file, thinking over three times the answer, under 5 tok/s, or a retry past 4,000 tokens with no tool call.

The probe cannot find the real L or the collapse rate. Those came hours into runs. So the first scored run carries piece 1's counters, and the value is corrected from them if healthy output gets near the line. If the probe's value holds, nothing else is needed.

see justification

3. Piece 1, count and log, goes first and changes no behaviour

Two counters, because they are two failures. output_limit_hits counts every stopReason: length with the block types of the cut message. reissue_msgs counts pi's "hit the output token limit" tool result. Each hit logs its output token count, its duration, and the runner's atBudget verdict, one alarm line per event. The logs hold 61 length stops in 20 sessions and 4 re-issue messages in 4 sessions.

see justification

4. Piece 2, a per-turn wall-clock cap of 25 minutes, end reason turn_timeout

The longest healthy call in a scored run is under 9 minutes. The longest healthy call anywhere is 21 minutes, on a research replay arm decoding at 1.8 tok/s. Every call between 21 and 31 minutes is absent from the logs, and above 31 minutes sit six DeepSeek text loops, two runner aborts that returned nothing, and the 70-minute discarded tool call. The report first proposed 20. I argued that a false stop costs a whole arm and a true stop five minutes later costs five minutes, and the agent agreed: 25 when replay arms share the runner, as a flag --turn-min with the value written into the row.

The clock starts at the stream's message_start, not at the request. Otherwise a stall abort plus pi's retries reads as one 61-minute turn. The row scores as a stop, not a rescue, and that takes one sentence in PLAN.md.

see justification · the 20 versus 25 exchange · clock caveat

5. Piece 3 changes from "two hits on tool calls" to "two hits at budget", end reason output_limit

As filed, the rule never fires. No log has two consecutive length stops that both carry a tool call, and the re-issue path recovered every time. The opposite rule, any two length stops in a row, fires in 8 sessions, and 2 of them are complete scored runs where pi's below-budget recovery worked as designed. The runner's existing atBudget test separates the two. Two consecutive at-budget stops fire in 3 sessions, all gemma-4-12b, all with 0 commits, at 28 to 39 minutes into runs that went on for 46 to 99 minutes. That saves 95 machine minutes and changes no score.

The rule is safe only while the cap is at least twice the model's longest healthy output, which is what decision 1 guarantees. That dependency becomes the law sentence. The budget item does not need to close first, since bench 9 already runs Qwen3.8 at 3.9 times its L.

see justification · the small-budget exchange · the four hit patterns

6. The loop verdict lands beside the row as a flag, never a stop, after a one-line fix

loop-check.py on an events log joins every tool-call delta into one string, so repeated commands never enter its window. Appending a newline after each toolcall_end fixes it. On corrected input, 11 of 65 sessions read LOOP, and every one is a real loop: the replay arms were built to reproduce the gemma thinking loop and did, and DeepSeek flash wrote the same sentence for 45 minutes before recovering. The three DeepSeek cloud sessions are the only loops no other piece catches before the 384k budget.

The threshold of 0.10 passes every scored run, but the nearest healthy run sits at 0.13, a factor of two rather than an order of magnitude. So the verdict ships with its worst ratio and kind written into the row, and the eleven LOOP rows get a hand check before anyone trusts it further.

see justification · the false-positive exchange

7. Two things that are not alarms

Qwen3.8 MLX returning one token with finish_reason: length, 11 and 16 times in two runs, is the mlx server refusing to generate at 88 percent of its window. Decision 1 fixes it through the budget and reserveTokens, not through an alarm. And rpiv-mono, checked on request, uses maxTokens only in window arithmetic, an example config, and a telemetry attribute. There is no small-turn theory in it.
