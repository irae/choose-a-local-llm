Runner alarms: summary

Decisions only. The evidence, the per-model table, and the harness survey stay in the full report. Base: 65 unique Mendel sessions, 5,751 assistant turns, both machines.

Recommendations

  1. Piece 1, count and log. Do first. No behaviour change.
    • Two telemetry counters, not one: output_limit_hits = every stopReason: length, with the block types of the truncated message; reissue_msgs = every pi tool result that says "hit the output token limit".
    • Per hit, log: output token count, turn duration, and the runner's own atBudget verdict (output at 80 percent or more of maxTokens).
    • One alarm line per event in the runner log.
    • Observed: 61 length stops in 20 sessions; 4 re-issue messages in 4 sessions.
    see justification
  2. Piece 2, per-turn wall-clock cap. N = 20 minutes. End reason turn_timeout.
    • Cuts 10 of 5,751 turns (0.17 percent): six DeepSeek text loops (31 to 50 min), two runner aborts with no token returned (37, 62 min), the 70-minute discarded tool call, one healthy 21-minute call on a 1.8 tok/s research replay arm.
    • Longest healthy call in a scored run: under 9 min. Longest healthy cloud call: 5 m 53 s. p99.5 of all turns: 8 m 53 s.
    • N = 25 cuts zero healthy turns and still catches the 31-minute loop. Pick 25 only if a replay arm that slow must survive.
    • N = 15 starts cutting healthy replay calls. N = 10 cuts the 10 to 11 minute thinking collapses, which are piece 3 territory.
    • Clock rule: measure from message_start (or turn_start) in the RPC stream, not from the request timestamp. Otherwise a stall abort plus pi retries double-counts, up to 61 min in the replays. The events log already has both markers.
    • Score the row as a stop, not a rescue. One sentence in PLAN.md.
    see justification · clock caveat · distribution
  3. Piece 3, two consecutive output-limit hits. Change the condition from "on tool calls" to "at budget". End reason output_limit.
    • As written ("on tool calls") the rule never fires in any log. The re-issue path recovered every time.
    • "Any two consecutive length stops" fires in 8 sessions, and 2 of them are complete, scored runs (qwen3.6 context-overflow pairs, pi's below-budget recovery working). Rejected.
    • "Two consecutive at-budget stops" (the runner's existing atBudget test) fires in 3 sessions, all gemma-4-12b, all 0 commits, at 28, 32 and 39 min into runs of 46, 49 and 99 min. Saves 95 machine minutes, changes no score.
    • Below-budget pairs (1-token server stubs, context overflows) stay with pi's compact-and-retry and the runner's tooling budget, which already end them.
    • Row records both output token counts.
    see justification · the four hit patterns
  4. Loop verdict at run close. Wire loop-check.py in, and fix its events-log input first.
    • Bug: on an events log, read_lines joins all tool-call deltas into one string, so repeated commands never enter the window. Fix: append a newline after each toolcall_end event. One line.
    • On per-block input: 11 of 65 sessions read LOOP. The three DeepSeek cloud sessions among them are caught by no other piece before the 384k budget.
    • The verdict runs on the finished log. It changes nothing the model did; it lands beside the row for the scorer.
    see justification
  5. Not a runner alarm: the Qwen3.8 MLX 1-token stubs.
    • mlx server at 88 percent of its window returns 1 output token with finish_reason: length, 11 and 16 times in two runs. Tooling failure. Fix is the window arithmetic in backlog/qwen38-mlx-output-budget-and-window.md.
    see justification
  6. rpiv-mono: not relevant.
    • maxTokens appears only in window arithmetic, a models.json example, and a telemetry span attribute (turn.stop_reason = "max_tokens"). No small-turn theory, no chosen value, no measurement. The span attribute is piece 1 under another name.
    see justification
