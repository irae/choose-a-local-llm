Summary

Fastest usable decode: mlx_lm.server at 19.7 tok/s — plain MLX beats llama-server's best MTP configuration (16.9 tok/s, draft depth 3; 12.4 without MTP). But MLX tops out at 48K context and serves one request at a time, so llama-server with q8_0 KV is the choice for big context (one 160K slot) and concurrent sub-agents (two 72K slots). q8_0 outputs verified byte-identical to f16 at temp 0 (f16: ~1% faster, capped at 96K / 2×44K).

How to start each variant

Fastest single agent — mlx-lm (OpenAI-compatible API, one request at a time):

mlx_lm.server --model mlx-community/Qwen3.8-27B-4bit --port 8081

Biggest context — one 160K slot, q8_0 KV (near-lossless; pi id qwen3.8-27b-160k):

llama-server -hf bartowski/Qwen3.8-27B-GGUF:Q4_K_M \
  --alias qwen3.8-27b-160k --no-mmproj \
  --spec-type draft-mtp --spec-draft-n-max 3 --parallel 1 \
  -ngl 999 -fa on -c 163840 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --jinja --port 8081

Lossless-KV alternative — one 96K slot, f16 KV, MTP:

llama-server -hf bartowski/Qwen3.8-27B-GGUF:Q4_K_M \
  --alias qwen3.8-27b --no-mmproj \
  --spec-type draft-mtp --spec-draft-n-max 3 --parallel 1 \
  -ngl 999 -fa on -c 98304 \
  --jinja --port 8081

Two concurrent agents — two 72K slots, q8_0 KV (pi id qwen3.8-27b-2x; 2×76K loads but decode degrades, 2×80K OOMs; f16 alternative: 2×44K):

llama-server -hf bartowski/Qwen3.8-27B-GGUF:Q4_K_M \
  --alias qwen3.8-27b-2x --no-mmproj \
  --spec-type draft-mtp --spec-draft-n-max 3 --parallel 2 \
  -ngl 999 -fa on -c 147456 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --jinja --port 8081

The slot layout is fixed at startup — restart to switch modes.

Backend comparison: llama-server (GGUF) vs mlx-lm (MLX)

MLX beats GGUF+MTP on decode — its Metal kernels handle this hybrid architecture better than llama.cpp's. But MLX loses everywhere else: max context measured 48K (64K prompts OOM; llama-server reaches 96K), prompt processing ~105 tok/s (no faster than llama.cpp's 123), one request at a time (no sub-agent slots), and multi-instance is impossible (two 15.5 GB weight copies exceed the wired limit). MTP-on-MLX exists only as a CLI (no API) — disqualified for harness use; raw numbers remain in the markdown.

Open issue

Prompt processing on short prompts is ~20 tok/s, but reaches only ~123–127 tok/s on 1.5K–4K prompts — still low for this hardware class. This is independent of MTP (the no-MTP baseline shows the same numbers), so it looks like a Metal kernel limitation of the new hybrid DeltaNet architecture in the current build. Worth re-testing on future llama.cpp releases.
